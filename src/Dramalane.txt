==================================================
DRAMA LANE — PRODUCT PURPOSE
==================================================

Drama Lane is a 24/7 MaiTroll feature designed to give two users involved in a dispute a structured place to talk things out and ultimately squash the drama.

The concept is:

“Get it off your chest. Hear the other side. Squash the drama.”

Drama Lane is NOT intended to encourage threats, violence, doxxing, or real-world harm.

The page should feel bold, entertaining, premium, and very MaiTroll/cyberpunk, but moderation rules still apply.

3 MINUTE SESSION
==================================================

Each Drama Lane session lasts 3 minutes total.

Duration:

180 seconds.

The session should automatically end when the timer reaches zero.

Do NOT allow the client to extend the timer.

Use server time or a trusted timestamp source to calculate remaining time.

If a user refreshes the page, closes/reopens the app, or switches devices, the session state must remain correct.

30 SECOND SPEAKING CONTROL
==================================================

30

YOUR TURN

30

Continue through the 3-minute session.

Do not rely entirely on local JavaScript timers for state transitions.

The server/session state should determine the current speaking participant.

==================================================
MUTE OTHER USER
==================================================

During the active session, the current speaker should have a control:

“MUTE OTHER USER”

This is a temporary speaking control.

The product requirement is that every 30-second speaking period gives the active speaker the ability to mute the other participant.

Implement this safely so that:

- The current speaker can mute the other participant.
- The inactive participant cannot mute the current speaker unless they become the active speaker.
- Mute state cannot be manipulated through client-side state alone.
- A user cannot mute themselves through this control.
- The mute control does not bypass Troll Officer moderation controls.

The UI should clearly indicate:

🔇 MUTED

when applicable.

==================================================
50/50 DRAMA LANE GIFT SPLIT
==================================================

This is a key monetization rule.

Normal MaiTroll gift behavior may currently give the recipient 100% of the applicable gift value.

Drama Lane is DIFFERENT.

For gifts sent during a Drama Lane session:

50% goes to Participant 1.

50% goes to Participant 2.

MaiTroll retains its platform share according to the final business/payment architecture.

IMPORTANT:

Do NOT simply credit the full gift to one participant and then try to manually fix the balance later.

The transaction must be designed so the final accounting is deterministic and auditable.

Example:

Viewer sends:

1,000 Troll Coins worth of gifts.

Drama Lane participant distribution:

Participant 1 → 500
Participant 2 → 500

Use integer-safe coin accounting.

If a value cannot divide evenly, establish a deterministic rounding rule and document it in the code.

==================================================
GIFTS MUST BE SESSION-SCOPED
==================================================

A gift sent during Drama Lane must be tied to the current Drama Lane session.

Do NOT accidentally route Drama Lane gifts through the normal broadcaster 100%-recipient logic.

The gift transaction should know:

context_type = drama_lane

or an equivalent existing architecture.

Prefer reusing existing transaction metadata/context fields if available.

==================================================
PAYOUT TIMING
==================================================

The Drama Lane participants should receive their Drama Lane gift earnings when the Drama Lane session ends.

Do NOT make the payout dependent on the client staying open.

The backend should calculate/finalize the session payout.

When the session ends:

1. Lock the session.
2. Stop accepting session gifts.
3. Aggregate valid gifts.
4. Calculate the 50/50 participant split.
5. Create the appropriate coin ledger entries.
6. Mark payout as finalized.
7. Prevent duplicate payout.

This must be idempotent.

If the same completion endpoint is called twice, it must NOT pay users twice.
